# Git Flow Lite Phase 5: Finish Preferences

Status: pending.

**Implementation branch:** `codex/git-flow-lite-phase-5`

## Goal

Add the small set of Finish controls discussed for Git Flow Lite: Merge versus Rebase for Feature/Bugfix, plus configurable annotated tags for Release/Hotfix.

The phase must preserve the Phase 3 recovery guarantees and avoid Tower-style arbitrary upstream/downstream workflow graphs.

## Prerequisites and session kickoff

- Phase 4 must be merged to `main` before this phase begins.
- Start from a clean `main`; do not create a separate Codex worktree for this phase.
- Create the implementation branch with `git switch -c codex/git-flow-lite-phase-5`.
- Read the roadmap, Phase 3 recovery plan, and Phase 4 Start plan before editing code.
- Treat existing `--no-ff` Finish as the regression baseline.

## Product decisions

- Feature and Bugfix support two Finish strategies:
  - `Merge commit`: existing `git merge --no-ff` behavior;
  - `Rebase and fast-forward`: rebase the topic branch onto Develop, then fast-forward Develop to the rebased topic tip.
- Use one repository-local default strategy for Feature and Bugfix to keep configuration simple. The Finish sheet may override it for a single operation.
- Release and Hotfix continue using `--no-ff` merge into Main followed by `--no-ff` merge into Develop. Do not offer Rebase for these multi-target flows: replaying a Release based on Develop onto Main can duplicate Develop history and break the version-tag/back-merge relationship.
- Add independent repository-local defaults for creating annotated tags on Release Finish and Hotfix Finish. Both default to on to preserve Phase 3 behavior.
- The Release/Hotfix Finish sheet may toggle tag creation and edit the proposed tag name for that run.
- Tag messages remain generated by Commit+ (`Release <tag>` or `Hotfix <tag>`); no custom message editor in this phase.
- No strategy automatically pushes or force-pushes a rewritten topic branch.

## Data model and persistence

- Add a Codable, Equatable `GitFlowTopicFinishStrategy`, for example `.mergeNoFastForward` and `.rebaseFastForward`.
- Extend `GitFlowConfiguration` with:
  - `topicFinishStrategy`, default `.mergeNoFastForward` when absent;
  - `createReleaseTagOnFinish`, default `true` when absent;
  - `createHotfixTagOnFinish`, default `true` when absent.
- Keep backward-compatible decoding for Phase 1-4 configuration files.
- Extend `GitFlowFinishPlan` with the resolved strategy. Release/Hotfix plans must always normalize to merge regardless of malformed/stale stored values.
- Retain `createTag` and `tagName` as per-run plan values.
- Extend the Finish checkpoint/result to record both the original source tip and, for a rebase, the rewritten source tip needed by recovery and Undo/Redo.
- Version the checkpoint payload or make new fields decode safely so an existing Phase 3 checkpoint is still resumable after upgrading.

## Planner and validation

- `GitFlowPlanner.finishPlan` resolves the default strategy and tag preference from the normalized configuration.
- Feature/Bugfix plans never contain a secondary target or tag.
- Release/Hotfix plans always contain Main as primary and Develop as secondary and always use merge strategy.
- Tag-name validation uses Git ref rules, not only non-empty string checks.
- The service repeats branch, tag, operation, and worktree checks immediately before mutation; sheet validation is advisory only.

## Merge execution

- Keep the current Phase 3 merge/checkpoint sequence unchanged for `.mergeNoFastForward`.
- Preserve the merge message, target ordering, annotated tag placement on the Main merge tip, source deletion behavior, warnings, and compound Undo/Redo.
- If tag creation is off, skip tag collision validation and do not create a tag Undo operation.
- Use `Hotfix <tag>` as the generated annotation for Hotfix rather than labeling every tag as Release.

## Rebase and fast-forward execution

Feature/Bugfix rebase Finish uses this sequence:

1. Require a clean worktree, current source branch, existing Develop branch, no unfinished operation, and no pending Git Flow checkpoint.
2. Record original source and Develop tips in the checkpoint.
3. Check out the source branch and run `git rebase <develop>`.
4. If rebase succeeds, record the rewritten source tip.
5. Check out Develop and run `git merge --ff-only <source>`.
6. Optionally delete the source branch.
7. Clear the checkpoint and register Undo only after the full operation succeeds.

Do not substitute a hard reset for the fast-forward merge in the original action.

## Conflict recovery

- Extend checkpoint phases to distinguish merge recovery from topic rebase recovery.
- If `git rebase` conflicts, keep the source branch checked out, keep the checkpoint, select File Status, and expose Resume Finish/Abort Finish through the existing menu and sidebar paths.
- Resume detects the rebase state and runs `git rebase --continue`, then records the rewritten tip and completes the fast-forward/delete sequence.
- Abort runs `git rebase --abort`, verifies/restores the original source tip, checks out the source branch, and clears the checkpoint.
- If a rebase has already completed but the subsequent fast-forward step fails, Resume must continue from the recorded rewritten source tip without replaying the rebase.
- Configuration changes made after the checkpoint is created must not change Resume behavior; the embedded plan is authoritative.
- Existing Phase 3 merge checkpoint Resume/Abort behavior must remain compatible.

## Undo and Redo

- Merge strategy keeps the existing compound target-reset/tag/source-branch operations.
- Rebase Undo must be guarded and restore the pre-Finish topology:
  1. require clean state and expected Develop tip;
  2. reset Develop to its recorded pre-Finish tip;
  3. restore or reset the source branch to its original pre-rebase tip.
- Rebase Redo should reuse the recorded rewritten source commit rather than running a fresh rebase whose commit IDs may differ:
  1. require the original source tip;
  2. move the source branch to the recorded rewritten tip with expected-ref guards;
  3. fast-forward Develop with `--ff-only`;
  4. delete the source branch again when requested.
- Add only the minimal guarded Git Undo operations required for fast-forward integration/ref restoration; keep Git execution out of SwiftUI views.
- Undo/Redo must refuse if the expected source or Develop refs changed.

## Test plan

- Old configurations decode to Merge with both Release and Hotfix tags enabled.
- New preferences round-trip in the Git common directory and are shared by linked worktrees.
- Planner resolves Merge/Rebase only for Feature/Bugfix and forces Merge for Release/Hotfix.
- Merge behavior remains byte-for-behavior compatible with Phase 3, including tag target and target order.
- Release/Hotfix can independently skip tag creation.
- Edited valid tag names are used; blank, invalid, and colliding tags fail before mutation.
- Rebase Finish produces linear Develop history with no merge commit and optionally deletes the source branch.
- Rebase conflicts create a durable checkpoint; Resume completes after resolution; Abort restores the original source tip.
- Failure after rebase but before fast-forward resumes without replaying the rebase.
- Merge checkpoints written before this phase still decode and resume.
- Rebase Undo/Redo restores both original and rewritten states and refuses ref drift.
- No strategy pushes or force-pushes a remote branch.

## Acceptance criteria

- Users can select Merge or Rebase for Feature/Bugfix globally and override it per Finish.
- Release/Hotfix retain safe multi-target merge behavior and expose configurable annotated-tag creation.
- Tag names are editable and validated before the first mutation.
- Rebase conflicts survive refresh and can be resumed or aborted from the existing Git Flow recovery controls.
- Undo/Redo is registered only after success and is guarded against changed refs.
- Existing Merge users see no behavior change after upgrade.

## Explicit non-goals

- No Rebase strategy for Release or Hotfix.
- No squash merge, fast-forward-only Merge preference, custom merge message, custom tag annotation, signing, or remote tag push.
- No separate upstream/downstream strategy matrix per topic kind.
- No arbitrary base/parent graph or Tower-style custom Branch Workflow editor.
- No automatic force-push after rewriting a published topic branch.
